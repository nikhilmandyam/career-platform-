# Exercise 05: Investigate a DNS or TLS Failure

## Setting and prediction

This investigation uses my real Project 1 site, `dueyy.me`. It is not the supplied simulation.

The failure occurred on October 6, 2026 while I was moving the domain from its previous GitHub Pages/Namecheap DNS setup to Cloudflare DNS and my Azure VM.

My Azure VM's public IP was:

```text
9.205.30.229
```

After the DNS cutover, I expected:

```bash
dig +short NS dueyy.me
```

to return Cloudflare's authoritative name servers:

```text
anita.ns.cloudflare.com.
yoxall.ns.cloudflare.com.
```

I also expected:

```bash
dig +short dueyy.me
```

to return:

```text
9.205.30.229
```

Finally, I expected `https://dueyy.me` to load my resume without a certificate warning.

## Failed check and evidence

Date: October 6, 2026.

My normal DNS checks still showed the old configuration.

```bash
dig +short NS dueyy.me
```

returned:

```text
dns1.registrar-servers.com.
dns2.registrar-servers.com.
```

The address check:

```bash
dig +short dueyy.me
```

returned the old GitHub Pages addresses:

```text
185.199.111.153
185.199.109.153
185.199.108.153
185.199.110.153
```

When I opened:

```text
https://dueyy.me
```

Safari displayed:

```text
This Connection Is Not Private
```

I then compared my normal resolver with public DNS resolvers.

```bash
dig @1.1.1.1 +short NS dueyy.me
```

returned:

```text
anita.ns.cloudflare.com.
yoxall.ns.cloudflare.com.
```

and:

```bash
dig @8.8.8.8 +short NS dueyy.me
```

also returned:

```text
anita.ns.cloudflare.com.
yoxall.ns.cloudflare.com.
```

A direct query to Cloudflare DNS:

```bash
dig @1.1.1.1 +short dueyy.me
```

returned:

```text
9.205.30.229
```

This was different from the answer returned by my Mac's normal DNS path.

## Diagnosis

I traced DNS first because TLS can only work with the server the hostname actually reaches.

Public resolvers such as Cloudflare and Google already showed the new Cloudflare name servers and the Azure VM address. My normal resolver was still returning the previous Namecheap name servers and GitHub Pages addresses.

This supported a DNS propagation, resolver-cache, or local resolver-path problem during the domain cutover.

I also checked the DNS resolvers macOS was using with:

```bash
scutil --dns | grep nameserver
```

At one point, an additional resolver appeared as:

```text
100.64.0.2
```

along with the Cloudflare DNS addresses. This showed that my Mac could be using a different resolver path than the direct `1.1.1.1` checks.

Because DNS was sending the browser to the old destination, the Safari TLS warning was downstream of the DNS problem. The browser was not necessarily connecting to the Azure Nginx server where my new Let's Encrypt certificate was installed.

I did not save the certificate subject from the failed Safari connection before correcting the DNS path, so I cannot prove exactly which certificate Safari received at that moment. The exact resolver or caching mechanism responsible also remains uncertain.

## Repair and repeated check

I did not change the working Azure server, Nginx configuration, Cloudflare DNS records, or TLS certificate.

The safe repair was to correct the client-side DNS path instead of changing the production site. I disabled the network/VPN resolver path that was interfering, configured Cloudflare DNS on my Mac, and flushed the local DNS cache.

I then repeated the same DNS checks.

```bash
dig +short NS dueyy.me
```

now returned:

```text
anita.ns.cloudflare.com.
yoxall.ns.cloudflare.com.
```

The repeated address check:

```bash
dig +short dueyy.me
```

now returned:

```text
9.205.30.229
```

I then reopened:

```text
https://dueyy.me
```

and the resume loaded successfully without the previous privacy warning.

I also verified the web behavior with:

```bash
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" http://dueyy.me
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" http://www.dueyy.me
curl -s -o /dev/null -w "%{http_code}\n" https://dueyy.me
curl -s -o /dev/null -w "%{http_code}\n" https://www.dueyy.me
```

The results were:

```text
301 https://dueyy.me/
301 https://www.dueyy.me/
200
200
```

The site also worked over cellular data, and later it worked normally on LMU-Wireless without another server-side change.

The repeated checks support the diagnosis that the original failure was temporary and related to DNS propagation, caching, or the resolver path during the domain cutover rather than a permanent failure of the Azure VM or certificate.

## What you learned

I learned that a browser TLS warning does not automatically mean the certificate on the intended server is wrong. DNS should be checked first because the client may be reaching a different server than expected.

A useful way to distinguish a DNS problem from a TLS problem is to compare the normal resolver with known public resolvers:

```bash
dig +short dueyy.me
dig @1.1.1.1 +short dueyy.me
dig @8.8.8.8 +short dueyy.me
```

If those answers disagree, I would investigate DNS propagation, caching, VPN DNS, or another resolver before changing the certificate or server.

If DNS consistently returned the correct Azure IP but HTTPS still failed, I would inspect the certificate next with:

```bash
openssl s_client -connect dueyy.me:443 -servername dueyy.me
```

If DNS and TLS were both correct but the page still failed, I would move to the application layer and check Nginx, the `career-platform` systemd service, Uvicorn, and application logs.
